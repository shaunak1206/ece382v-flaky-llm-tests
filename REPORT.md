# Are LLM Generated Unit Tests Flaky? A Rerun Study on Twelve Python Libraries

Shaunak Kapur, ECE 382V Software Testing in the Era of Nondeterminism, Fall 2026

Working draft, October 2026. Numbers in the Results section are generated by `scripts/analyze.py`, `scripts/run_smells.py`, and `scripts/coverage.py` and can be regenerated from `results/`.

## 1. Introduction

Developers now ask large language models to write unit tests for them, through tools like GitHub Copilot and ChatGPT and through research pipelines like TestPilot. These pipelines usually generate a test, run it once, and keep it if it passes. A test that passes once is not always a test that passes every time. It can depend on the wall clock, on the order the tests run in, on how Python hashes strings into a set, on random numbers, on files left behind by another test, or on how busy the machine is. Tests like this are called flaky tests and they are one of the main reasons developers stop trusting their test results. All of the large flaky test studies so far look at tests written by people. This project asks whether tests written by an LLM are more or less flaky than the human written tests for the same code, what makes them flaky when they are, and whether the single run filter that most generation pipelines use is enough to keep flaky tests out.

## 2. Research questions

- **RQ1 Prevalence.** How often are LLM generated tests flaky compared with the human written tests of the same library, under the same rerun budget and the same perturbations?
- **RQ2 Root causes.** When LLM generated tests are flaky, what is the root cause, using the categories from Luo et al. (FSE 2014)?
- **RQ3 Latent risk.** Even when no test flips during our reruns, do LLM generated tests contain more code patterns that are known to cause flakiness (real sleeps, unfrozen clock reads, unseeded randomness, threads) than human tests?
- **RQ4 Generation pipeline.** Does the way the tests are generated matter? We compare an agentic pipeline that runs the tests and fixes failures, a one shot pipeline with no execution feedback, and two model sizes. We also measure what a single run generate and filter step keeps and throws away.

## 3. Methodology

### 3.1 Subjects

Twelve pure Python libraries that have their own pytest compatible test suites, need no network or services, and run in under a minute. Six were picked first as a pilot. Six more were added because their behaviour depends on time, randomness, threads, or the file system, which is where flaky tests usually come from.

| Library | Version (commit) | Why it is here |
|---|---|---|
| cachetools | v7.1.8 | TTL expiry, random eviction |
| schedule | 1.2.2 | job scheduling against the wall clock |
| tinydb | 4aa5311 | JSON files on disk |
| humanize | 3201e70 | "3 minutes ago", locales |
| toolz | 1.1.0 | dicts and sets, random_sample |
| tabulate | 268615a | pure formatting, a control |
| tenacity | 8be01b1 | retry timing, random jitter |
| filelock | 3.16.1 | file locks shared between threads |
| boltons | 4e5faa3 | caches, relative time, temp files |
| more-itertools | 1ea82a7 | random_product, time_limited |
| arrow | 2224255 | now, utcnow, humanize, timezones |
| pybreaker | 2b0b965 | reset timeouts, async calls |

Faker was considered and dropped because one run of its suite takes 72 seconds.

### 3.2 Test generation

Each library gets the same prompt in every condition. The prompt points the model at the library source, forbids reading the existing tests, asks for 50 to 80 pytest test functions covering the public API "the way a developer would", and names the time, random, thread, or file features of that library so that the model writes tests for them. The exact prompt text is in `prompts/README.md`.

| Condition | Model | Feedback | Suites |
|---|---|---|---|
| AG-S | Claude Sonnet as an agent | runs the suite once and may fix or delete failing tests for up to 3 rounds | 12 |
| OS-S | Claude Sonnet | none, writes the files in one go and never runs them | 12 |
| OS-H | Claude Haiku 4.5 | none, writes the files in one go and never runs them | 12 |

For the two one shot conditions we then apply the step most generation pipelines use. We run the suite once with a fixed order and fixed hash seed and mark every test that fails as rejected. Unlike a real pipeline we keep the rejected tests in the rerun experiments, which lets us see whether the filter threw away tests that were only failing some of the time.

### 3.3 Rerun harness

`scripts/rerun.py` runs a suite many times and records the outcome of every test from JUnit XML. Each suite is run in three modes.

| Mode | Runs | What changes between runs |
|---|---|---|
| both | 30 | test order (pytest-randomly, new seed each run, which also reseeds `random`) and `PYTHONHASHSEED` |
| tz | 20 | the above plus the `TZ` environment variable, cycling through ten time zones including UTC+14 and UTC-11 |
| stress | 20 | the above plus one CPU burning process per core during the run |

A test is **flaky** if it both passed and failed across the 70 runs of its suite. A test that fails in every run is **always fail** and is reported separately. Generated suites run inside their own empty working directory so tests that write files cannot affect each other or the repository. Every test has a 60 second timeout.

Each flaky test is then diagnosed with targeted reruns (`scripts/diagnose.py`). It is run alone with a fixed seed, alone with varying hash seeds, alone with varying time zones, alone under CPU stress, and inside its suite in random order, 50 times each. This tells us whether it fails because of timing, ordering, hashing, or the time zone.

### 3.4 Static risk scan

`scripts/smells.py` parses every test function and flags eight patterns linked to flakiness in prior studies. These are real sleeps, wall clock reads without a frozen or injected clock, assertions on elapsed time, calls to randomized functions without a visible seed, threads or async tasks, literal file paths outside a temp directory, subprocesses, and assertions that compare the iteration order of a set or dict view to a list. The scan is a heuristic and is used to compare conditions, not to label individual tests as flaky.

### 3.5 Coverage

`scripts/coverage.py` measures line coverage of each library from each suite with pytest-cov. One shot suites are measured with the rejected tests removed, which is the suite a pipeline would actually keep. For boltons only the eight modules named in the prompt are counted.

### 3.6 Environment

Apple M3 with 8 cores, macOS 26.5, Python 3.12.7, pytest 9.1.1, pytest-randomly 5.0.0, pytest-timeout 2.4.0, freezegun 1.5.5. Generation took place September 1 and October 1, 2026.

## 4. Results

In total the study ran 48 suites (12 libraries times 4 conditions) holding 10,200 tests, 70 times each, which is about 714,000 test executions. Full per suite tables are in `results/analysis.md`, the smell table in `results/smells.md`, and the hand written root cause notes in `results/root_causes.md`.

### 4.1 RQ1 Prevalence

| Suite condition | Suites | Tests | Flaky | Flaky % | 95% Wilson CI |
|---|---|---|---|---|---|
| Human | 12 | 5,587 | 6 | 0.11 | 0.05 to 0.23 |
| Agentic Sonnet (AG-S) | 12 | 1,511 | 0 | 0.00 | 0.00 to 0.25 |
| One shot Sonnet (OS-S), kept tests | 12 | 1,406 | 0 | 0.00 | 0.00 to 0.27 |
| One shot Haiku (OS-H), kept tests | 12 | 1,595 | 3 | 0.19 | 0.06 to 0.55 |

Flakiness was rare everywhere. The intervals overlap, so with this many reruns we cannot say any condition is more flaky than human tests. The two Sonnet conditions produced no flaky tests at all across about 2,900 tests, and the one shot Haiku condition produced 3. Human suites produced 6, all in three of the twelve libraries (filelock, arrow, pybreaker).

### 4.2 RQ2 Root causes

| Root cause (Luo et al.) | Human | LLM |
|---|---|---|
| Test order dependency | 4 | 0 |
| Concurrency | 2 | 0 |
| Time, including time of day and deadlines under load | 0 | 2 |
| Randomness combined with a timing assertion | 0 | 1 |

The causes split cleanly. Every human flaky test came from shared global state or a real thread race, the classic causes in prior studies. The filelock and arrow victims pass every time when run alone and fail whenever a specific earlier test leaves an object in a class level or module level registry. The pybreaker tests catch a real race in the half open transition and only flipped under CPU stress. Every LLM flaky test instead came from the test touching real time. One asserts that two jittered retry waits add up to at least 10 ms, one asserts a retry loop finishes within 120 ms of wall time, and one builds an `until` time two hours in the future as a bare clock time, which lands in the past when local time is after 22:00. That last test only failed in the America/St_Johns runs, which is exactly what the time zone mode was built to catch.

### 4.3 RQ3 Latent risk

| Condition | Test functions | Any risk pattern % | Real sleep % | Unfrozen clock read % | Timing assert % | Unseeded random % | Threads or async % |
|---|---|---|---|---|---|---|---|
| Human | 3,077 | 3.9 | 0.7 | 1.9 | 0.1 | 0.8 | 0.6 |
| Agentic Sonnet | 1,074 | 8.4 | 2.4 | 4.0 | 0.7 | 1.2 | 1.5 |
| One shot Sonnet | 907 | 8.5 | 1.4 | 4.1 | 1.3 | 2.1 | 1.2 |
| One shot Haiku | 1,750 | 9.4 | 2.6 | 3.4 | 1.0 | 1.6 | 1.1 |

All three LLM conditions have about twice the share of risky tests that human suites have, even though the prompts asked every condition to cover the same time and randomness features. The LLM tests sleep for real more often, read the clock without freezing it more often, and assert on elapsed time seven to thirteen times more often.

How well does the scan line up with real flips? It flagged 331 LLM test functions and all 3 flaky LLM tests were among them, so recall on LLM tests was 3 of 3 but precision was under 1%. On human tests it flagged 121 functions and caught 2 of the 6 flaky tests (the pybreaker race, through its sleeps). It cannot see the 4 order dependent human tests, since those depend on what another test leaves behind, which a per test scan does not look at. So the scan is a cheap warning for the time related flakiness LLMs write, and order dependence needs a rerun tool like iDFlakies. Most flagged tests never flipped on this laptop, which is why the risk shows up here more than in RQ1.

### 4.4 RQ4 Generation pipeline and the one run filter

| | One shot Sonnet | One shot Haiku |
|---|---|---|
| Test functions written | 907 | 1,750 |
| Files that did not import | 0 | 2 (54 test functions lost) |
| Tests that ran in the filter run | 1,406 | 1,696 |
| Rejected by the one run filter | 0 | 101 (6.0%) |
| Rejected tests that were really flaky | 0 | 0 |
| Kept tests that later turned out flaky | 0 | 3 |

Without any execution feedback, Sonnet wrote 907 tests in which nothing failed, not even once. Haiku wrote almost twice as many tests as asked, two of its files did not import, and 6% of its tests failed the filter run. Every one of those 101 rejections was a deterministic failure, so the one run filter never threw away a flaky test. The filter also let all three flaky Haiku tests through, because each one passes most of the time. The agentic Sonnet pipeline, which can run and fix its tests, ended up with zero flaky tests and the same risk profile as one shot Sonnet. That suggests execution feedback fixes wrong expectations but does nothing about timing risk, since a timing problem rarely shows up in the one or two runs an agent does.

Separately, one one shot Haiku test (`test_zero_interval` in schedule) hangs forever, and under random order the job it leaves in the global default scheduler can hang later tests too. A single run of that suite took about five minutes before we lowered the per test timeout. This is an order dependent hang that a one run filter with a fixed order would only partly see.

### 4.6 Targeted diagnosis

Failures out of 50 runs for each flaky LLM test in each configuration.

| Test | Alone, fixed seed | Alone, varying hash seed | Alone, varying time zone | Alone, CPU stress | Whole suite, random order |
|---|---|---|---|---|---|
| schedule `test_until_with_string_time_format` | 0 | 0 | 5 | 0 | 19 |
| tenacity `test_wait_random_exponential_in_timing_test` | 7 | 7 | 2 | 1 | 3 |
| tenacity `test_stop_before_delay_prevents_exceeding_limit` | 0 | 0 | 0 | 0 | 0 |

- The schedule test fails only when the local clock is past 22:00. In the time zone runs that happens in 1 of the 10 zones, so 5 of 50. The whole suite run happened to be done after 22:00 Central time, so it failed whenever the run landed after that point. Test order has nothing to do with it. This is a time of day bug that a developer working late would hit.
- The jitter test fails about 14% of the time on its own, so its flakiness is intrinsic to the test. Order and hash seed do not matter.
- The deadline test never failed in 250 targeted runs. Its one failure in the main study happened while two stress jobs overlapped and the load average was near 100. This matches what Rahman et al. (ICST 2024) report about timing failures being very hard to reproduce by plain rerunning, and it is a good candidate for their FlakeRake style delay injection.

### 4.7 Takeaways so far

1. On these libraries LLM written tests were not measurably more flaky than human tests, and the strong model wrote none at all.
2. LLM flakiness looks different from human flakiness. It comes from real time inside the test, while human flakiness comes from shared state between tests.
3. LLM tests carry about twice the latent timing and randomness risk, which a fast laptop mostly hides.
4. A one run filter catches broken tests and misses flaky ones. A cheap static risk scan flagged all three flaky LLM tests, though it also flags hundreds that never flipped.

## 4.8 Next steps (for the proposal and progress reports)

1. **More reruns on the risky tests.** Rerun the 452 scanner flagged test functions 1,000 times each instead of rerunning whole suites, since that is where the LLM flakiness lives.
2. **A slower machine.** Repeat the reruns on a Linux VM with 2 cores (a free Colab runtime works) to see whether the latent timing risk turns into real flips on hardware closer to CI.
3. **More generators.** Add a non Claude model (GPT class) and a plain Copilot style prompt that does not name the time features, to separate model effects from prompt effects.
4. **Mitigation.** Regenerate the one shot suites with a short prompt that warns about real sleeps, unfrozen clocks, and timing asserts, and compare a 5 run filter with the 1 run filter on cost and on flaky tests kept.
5. **Order dependence check.** Run iDFlakies style polluter and victim search on all generated suites, since the per test scan cannot see shared state.

## 5. Threats to validity

- Our generators are Claude models running as agents. Other models, and tools like Copilot that see less of the source, may write different tests.
- The prompt names the time and randomness features of each library on purpose. This makes risky tests more likely than a generic prompt would, so the results are closer to an upper bound for these libraries.
- 70 reruns can miss tests that fail less than about 1 in 50 times. A test that never flipped is not proven stable.
- All runs happen on one laptop. A slower CI machine could expose timing problems we do not see.
- The smell scanner is a set of regular expressions over test source and will have false positives and false negatives.
