\section{Summary}
We finished everything we planned for this milestone and moved two items from the second milestone forward. We now have 72 LLM written test suites for 12 Python libraries, made with three models or setups and three prompt styles, plus the 12 human written suites as the baseline. Every suite has been rerun under random test order and hash seed, ten time zones, and two kinds of machine load, and every flaky test has a labeled root cause. After the proposal feedback we changed the method in five places. Subjects now come from a written selection funnel, two new prompt styles are based on prior work and on how developers actually ask for tests, generated tests are also run inside the human suites, machine load now follows Shaker~\cite{silva2020}, and every scanner rule is tied to a root cause category and checked against flaky tests labeled by Gruber et al.~\cite{gruber2021}.

Counting every rerun, mixed suite, and targeted run, the study has now executed about 2.6 million tests. The main results so far are these. Flaky LLM tests are rare and all of them come from one setup (one shot Haiku with the feature prompt). The two new prompt styles produced no flaky tests in 2,104 tests and about a sixth of the risky patterns of the feature prompt, which means our original prompt was a large part of why LLM tests looked risky. The new mixed suites found something the separate runs could not. Three agentic tests for schedule pass every time in their own suite but fail in up to 22 of 30 runs once they share a session with the human tests, because the human tests leave jobs in the library's global scheduler. Stress-ng found one new flaky human test.

\section{What we changed after the proposal feedback}
\label{sec:feedback}

\subsection{How subjects are chosen}
\label{sec:subjects}
\texttt{scripts/select\_subjects.py} applies fixed rules and logs the count after each one. It starts from the 5,000 most downloaded PyPI packages over the last 30 days and keeps packages that are libraries (no typing stubs or pytest plugins), link a GitHub repository, ship a pure Python wheel, have at most three required dependencies and run on Python 3.12, and have test files in their repository. The counts are 5,000, 4,701, 4,131, 3,296, 2,188, and 1,959. The survivors are split into two strata by whether the library source imports a module tied to nondeterminism (time, datetime, random, threading, asyncio, concurrent, multiprocessing, tempfile, socket). 1,135 do and 824 do not. We oversample the first stratum on purpose, since that is where flaky tests come from, and we say so. The last rule is that the suite passes offline (pytest-socket) in under 60 seconds at a pinned commit. It needs a clone and a run, so it is applied to a seeded random sample. In a sample of 6 per stratum, 5 of 12 passed. These 5 are the pool we will draw new subjects from. All 12 of our current subjects pass every rule. 10 are in the nondeterminism stratum and 2 (tinydb and tabulate) are not. Their download ranks run from 44 (filelock) to 2,167 (tinydb). The same script can be rerun with a different seed to add subjects in the same way.

\subsection{Which prompts, and why}
Our original prompt names the time, random, thread, and file features of each library so that the model tests them. That makes risky tests more likely, so we now treat it as an upper bound and call it the \emph{feature prompt}. We added two styles, both run one shot with Claude Sonnet so they compare directly with the feature prompt suites (OS-S). \textbf{TP-S} follows TestPilot~\cite{schafer2024}. The model sees only the signatures, docstrings, and README usage examples of the public API (built by \texttt{scripts/build\_testpilot\_context.py}), never the implementation. \textbf{PL-S} is a plain developer prompt, ``write unit tests for this library using pytest'', with the source files and no hints about what to test. All styles keep the same practical limits (50 to 80 tests, pytest only, no reading of the existing tests, no running). The exact prompt texts are in \texttt{prompts/README.md}.

\subsection{Running generated tests with the existing ones}
So far each generated suite ran as a whole in random order, which can expose order dependence inside that suite, and each flaky test was then rerun alone only to diagnose it. We now also run a \emph{mixed} condition (\texttt{scripts/mixed.py}). The generated tests a pipeline would keep are copied into the library's own test folder and pytest runs both in one session in random order, which is how a developer would add them. Either side can now pollute the other. The human suite is run alone on the same machine as the baseline.

\subsection{Machine load}
The original stress mode starts one Python busy loop per core, which only loads the CPU and was not based on prior work. We added a \texttt{stressng} mode that follows Shaker~\cite{silva2020}. It uses the same four stress-ng options as Shaker (\texttt{--cpu}, \texttt{--cpu-load}, \texttt{--vm}, \texttt{--vm-bytes}) and Shaker's first step, a uniform random sample of ten configurations over those domains. Run $i$ uses configuration $i \bmod 10$ and the configuration of every run is saved, so once we have enough flaky tests we can build Shaker's configuration by test matrix and pick the configurations that expose the most. The limits are that we load only CPU and memory, not disk, network, or garbage collection, and that we use two machine types (an 8 core Apple M3 and 2 vCPU Linux runners).

\subsection{The static scanner}
\label{sec:rq3}
Each rule now names the root cause category it is meant to catch. Real sleeps map to async wait and time~\cite{luo2014}, unfrozen clock reads and elapsed time asserts to time, unseeded randomness to randomness~\cite{gruber2021}, threads and async tasks to concurrency, fixed file paths and subprocesses to IO and resource leaks, and asserting the order of a set or dict view to unordered collections~\cite{luo2014,gyori2016}. We checked the scanner against outside labels. Gruber et al.\ published a hand labeled sample of 100 non order dependent flaky tests from 100 PyPI projects. We checked out 96 of them at the recorded commit (\texttt{scripts/validate\_scanner.py}). The scanner flagged 10 of 96. It caught all 3 async wait tests and some of the time and concurrency tests, but only 2 of 35 randomness tests and 1 of 41 network tests. In most misses the nondeterminism is inside the code under test and not in the test body, for example a test that trains a model that seeds itself. Of 714 other tests in the same files that were never reported flaky, 35 were flagged (4.9\%). So the scanner is a fair warning for timing problems written directly in the test, which is what the LLM tests have, and it is blind to nondeterminism that lives in the library. A network rule we added after this check raises recall to 13 of 96.

\subsection{The human baseline}
Human tests are flaky, but rarely. 7 of 5,589 flipped, 4 order dependent (global registries in filelock and arrow), 2 thread races in pybreaker that only show under CPU stress, and 1 tenacity async test that asserts a short sleep finishes quickly and failed once under stress-ng. Since flip counts are small everywhere we now also compare the failure rate of each flaky test, the share of tests with risky patterns, and the results of the mixed suites, not just how many tests flipped.

\subsection{If generated tests are never flaky}
They are sometimes. Three one shot Haiku tests flip, and both of the tests from our pilot were LLM written. The mitigation step (Intermediate Steps 3) would still have very little to count if it only used observed flips, so it will also be measured on the scanner risk rate, on failures we can trigger on purpose with stress-ng and FlakeRake style delays~\cite{rahman2024}, and on line coverage. We have already drafted the mitigation prompt (\texttt{prompts/mitigation\_prompt.md}) so that it does not depend on the final list of flaky tests.


\subsection{Earlier feedback on the project plan (October 11)}
\label{sec:oct11}
\textbf{Generate tests early.} All 72 LLM suites exist (36 on October 1 and 24 on October 22), so test generation will not hold up later steps.

\textbf{Basic or fancy prompting.} Generation is basic on purpose. Each suite comes from one prompt per library with no retrieval, no few shot examples, and no extra context collection. The only differences are what each prompt style hands the model (the module source, or only the API docs for TestPilot style) and whether the agentic setup can run its tests and fix them for up to three rounds. A richer context collection pipeline is out of scope.

\textbf{Root causing and existing tools.} Every flaky test is first rerun on its own and inside its suite under each change separately (\texttt{scripts/diagnose.py}), and then labeled by hand with the categories of Luo et al.~\cite{luo2014}. We also ran FlaPy~\cite{gruber2021}, an existing flaky test detector for Python, on two suites with known flaky tests so we know how to use it and can check our harness against it (\texttt{.github/workflows/flapy.yml}, 10 same order and 10 random order runs each). On the human arrow suite it reported exactly the two order dependent locale tests we found and nothing else among 1,904 tests. On the one shot Haiku tenacity suite it found the jitter test (6 failures in 20 runs) and missed the deadline test, which has failed only once in all our runs, under CPU stress. So FlaPy agrees with our harness on every test it can see, and it does not replace the load and time zone changes for rare timing failures. Getting it to run took three attempts, since its container needs a terminal and ships pytest 6.2.5, which forces older plugin versions.

\textbf{Metrics.} Per test we record the outcome of every run in every mode and on each machine, whether it is flaky (passed and failed on the same machine), its flaky failure rate (failures over runs), always fail and machine dependent tests, which change exposed it, which runs failed, and the stress-ng configuration of each run. The median failure rate of a flaky test is 11.1\% for human tests and 2.2\% for LLM tests. Per suite and condition we report the flaky rate with a 95\% Wilson interval, the risky pattern rate, the scanner's recall and flag rate, what the one run filter accepted and rejected and how many tests were lost to files that do not import, line coverage, and run time per suite run. For mixed suites we count flaky generated tests, human tests that flip only when mixed, and human tests that break.

\textbf{The other three points.} The stress-ng mode is described in Section~3.4. The plan if generated tests are never flaky, and the mitigation prompt we drafted up front (\texttt{prompts/mitigation\_prompt.md}), are in Section~3.7.

\subsection{RQ1, how often}
Table~\ref{tab:rq1} has the numbers. Every interval overlaps, so we still cannot say LLM tests are more or less flaky than human tests by flip counts. The two new prompt styles add 2,104 tests with no flips. All three flaky LLM tests are one shot Haiku tests with the feature prompt. Four human tests passed on one machine and always failed on the other (filelock checks that behave differently on macOS, and a toolz version check that fails when the package is installed from a source checkout). We count these as machine dependent and not flaky.

\subsection{RQ2, root causes}
\label{sec:rq2}
The causes split cleanly by who wrote the test. All three flaky LLM tests touch real time. One builds an \texttt{until} time two hours ahead as a clock time, which is in the past after 22:00, one asserts that two jittered retry waits add up to at least 10 ms (failing 10 to 24\% of runs depending on the machine), and one asserts that a retry loop finishes within 120 ms, which failed once under heavy load. The human flaky tests are order dependent (4, an earlier test leaves an object in a class or module level registry), thread races (2), and one timing assertion that only failed under stress-ng.

\subsection{Mixed suites}
Table~\ref{tab:mixed} shows the generated tests run inside the human suites on GitHub Actions, 30 runs each. No human test became flaky or broke because of the generated tests. The other direction did happen. Three agentic tests for schedule assume the module level default scheduler is empty. The human tests clear it at the start of each test but not at the end, so whenever a human test runs first the generated test sees leftover jobs. Two of these failed in 20 and 22 of 30 runs, and one generated test even ran a job function a human test had registered and crashed with a \texttt{TypeError}. These tests never failed in 70 runs of their own suite, so a developer would only see the problem after adding them to the real test suite. One more agentic tenacity test failed in 2 of 30 mixed runs and is still being labeled.

\subsection{RQ3, risky patterns}
The feature prompt suites have about twice the risky pattern rate of human tests (8.4 to 9.4\% against 3.9\%). The TestPilot style and plain prompt suites from the same model have 1.4\% and 1.5\%, lower than the human tests. So most of the extra risk came from our prompt pointing the model at time and randomness features, which is what the instructor suspected. The scanner flagged all 3 flaky LLM tests, and its validation on outside labels is in Section~\ref{sec:rq3}.

\subsection{RQ4, the pipeline}
The one run filter rejected 101 one shot Haiku tests, 11 TestPilot style tests, and 1 plain prompt test, and none of the rejected tests were flaky. It kept all three flaky Haiku tests, because each one usually passes. One TestPilot style file for schedule did not import, which lost 22 tests. The plain prompt gave the highest coverage of any LLM condition (82.6\%), and the TestPilot style prompt, which never sees the implementation, gave 70.7\%.

\subsection{Machine load and the slow machine}
Stress-ng (20 runs per suite, ten Shaker style configurations) found one new flaky human test and reproduced the jitter test in 3 of 20 runs. We also reran all 474 flagged tests about 350 times each on the 2 vCPU Linux runners with stress-ng running the whole time, 164,420 executions. No new flaky tests appeared. Only the two known Haiku tests flipped, and the 27 tests that always failed were all tests the one run filter had already rejected. With the October 4 run, every flagged test has now been run more than 1,300 times on the slower machine.

\section{Scripts, code, and data}
Everything is in the public GitHub repository \url{https://github.com/shaunak1206/ece382v-flaky-llm-tests}. The main pieces are below.
\begin{itemize}
\item \texttt{scripts/rerun.py}: reruns a suite $N$ times in one mode (\texttt{both}, \texttt{tz}, \texttt{stress}, \texttt{stressng}) and records every test outcome from JUnit XML.
\item \texttt{scripts/filter\_oneshot.py}: the one run generate and filter step.
\item \texttt{scripts/diagnose.py}: targeted reruns of each flaky test alone and in the suite under each change.
\item \texttt{scripts/smells.py}, \texttt{run\_smells.py}, \texttt{validate\_scanner.py}: the static risk scanner and its validation.
\item \texttt{scripts/select\_subjects.py}: the subject selection funnel.
\item \texttt{scripts/build\_testpilot\_context.py}: the TestPilot style prompt context.
\item \texttt{scripts/mixed.py} and \texttt{.github/workflows/mixed.yml}: mixed suites on GitHub Actions.
\item \texttt{scripts/extended.py} and \texttt{.github/workflows/extended.yml}: 1,000 reruns of flagged tests on Linux runners, with optional stress-ng.
\item \texttt{scripts/coverage.py} and \texttt{analyze.py}: coverage and the tables in this report.
\item Generated suites in \texttt{llm\_tests/}, \texttt{gen\_oneshot\_sonnet/}, \texttt{gen\_oneshot\_haiku/}, \texttt{gen\_tp\_sonnet/}, \texttt{gen\_plain\_sonnet/}. Raw rerun results in \texttt{results/}, prompts in \texttt{prompts/}, the running write up in \texttt{REPORT.md}.
\end{itemize}

\section{Challenges}
\begin{itemize}
\item \textbf{Flakiness is rare.} Under 0.2\% of tests flip in any condition, so most comparisons need risk measures, failure rates, or much longer runs.
\item \textbf{Generators do not always follow instructions.} Several one shot agents ran small shell commands (\texttt{mkdir}, \texttt{grep}, a syntax check) even though they were told not to run anything. None ran a test, so no suite got execution feedback, and every case is logged in \texttt{prompts/README.md}. One TestPilot style agent only read the first half of a long API file for more-itertools.
\item \textbf{Rate limits.} The subject funnel first used the GitHub API and hit the hourly limit, so it now lists repository files with blobless git clones.
\item \textbf{Two operating systems.} Coverage of filelock is low everywhere because the Windows module never runs on macOS or Linux, and timing behaves differently on the laptop and the runners. We report each machine separately.
\end{itemize}

\section{Next steps (Intermediate Steps 2, by November 6)}
\begin{enumerate}
\item Add a second model family (a GPT class model) under the plain and TestPilot style prompts, since prompt style mattered more than model so far.
\item Add four new subjects from the funnel pool (two per stratum) with the same steps, to show the funnel works for expansion.
\item Run Shaker's configuration selection on the per run stress-ng records once enough flaky tests are collected, and repeat the stress-ng runs on the laptop.
\item Run an iDFlakies style polluter and victim search on the mixed suites, starting from the schedule tests above.
\item Run FlaPy on every suite (so far it has run on two), and add an import level check to the scanner, since most of its misses have the nondeterminism inside the library.
\item Start the mitigation early with the drafted prompt, comparing risk rate, flaky tests, coverage, and cost against a 3 and 5 run filter.
\end{enumerate}
