For my project I want to study whether unit tests written by large language models are flaky. A lot of developers now use tools like GitHub Copilot or ChatGPT to write their tests and research tools like TestPilot generate a test and run it one time and keep it if it passes. The problem is that a flaky test can pass that one run and then fail later in CI. Also every big flaky test study I have read so far only looks at tests written by people. My plan is to take 12 small Python libraries and give each library four test suites. These are the human written suite that comes with the library and a suite from an agent that runs its tests and fixes the failing ones and two one shot suites that are never run while they are written, one from Claude Sonnet and one from Claude Haiku. I rerun every suite 70 times while changing the test order and the hash seed and the time zone and the CPU load, and I mark a test as flaky if it both passes and fails across those runs. I already have a first version of this working with about 714,000 test executions. So far 6 of the 5,587 human tests are flaky and 4 of those are order dependent. In addition 3 of the 1,595 one shot Haiku tests are flaky and all 3 are about real time. All 3 of those tests also passed the one run filter, which means a real pipeline would have kept them. Furthermore the LLM suites have about twice as many tests with risky patterns like real sleeps and clock reads that are not frozen. To evaluate this I will report the flaky rate of each suite with confidence intervals and the root cause of every flaky test using the categories from Luo et al. I will also check how well the risky patterns predict real flips. Later I want to try a prompt that warns the model about these patterns and a filter that reruns each test a few times before keeping it. However the part I am most unsure about is that flaky tests are rare, so I may need a lot more reruns or a slower machine like a Colab VM to see a real difference between the suites. I am working on this project individually.
